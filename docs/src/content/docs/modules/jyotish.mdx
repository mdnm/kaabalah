Jyotish calculations are part of `kaabalah/astrology`. They return **calculation data and method metadata only**. Separate description getters provide the bilingual text described below. Two nakshatra frames are provided and kept independent of the tropical zodiac:

- **Dhruva**: the Ernst Wilhelm / Kala Dhruva method, which measures nakshatras on the **celestial equator** from a Galactic Center anchor.
- **Lahiri**: the conventional Chitrapaksha sidereal comparison, which measures nakshatras on the **ecliptic**.

Tropical rasis, tropical longitudes and tropical houses are reported on every point and are never changed by the selected nakshatra frame.

```typescript
import { getJyotishChart, findActiveDasha, JYOTISH_METHODS } from 'kaabalah/astrology';
```

## Mixed-frame example

```typescript
import { getJyotishChart, findActiveDasha } from 'kaabalah/astrology';

const jyotish = getJyotishChart({
  date: new Date(Date.UTC(1990, 5, 15, 11, 0, 0)), // a UTC instant
  latitude: 51.5,
  longitude: -0.12,
  nakshatraFrame: 'dhruva', // or "lahiri"; both frames are always computed
});

const moon = jyotish.dhruva.points.moon;
moon.tropical.sign;                      // "Pisces"  (tropical rasi)
moon.tropical.degreeInSign.toFixed(2);   // "14.80"
moon.nakshatra;                          // "Purva Bhadrapada"  (Dhruva, equatorial)
moon.pada;                               // 2
moon.lord;                               // "jupiter"

const lahiriMoon = jyotish.lahiri.points.moon;
lahiriMoon.sidereal.sign;                // "Aquarius"  (Lahiri sidereal rasi)
lahiriMoon.nakshatra;                    // "Purva Bhadrapada"
lahiriMoon.pada;                         // 1

jyotish.yearLengthDays;                  // 365.2422 (Dhruva default)
jyotish.vimshottari.balance.lord;        // "jupiter"
const active = findActiveDasha(jyotish.vimshottari, new Date(Date.UTC(2020, 0, 1)));
active.maha.lord;                        // "mercury"
active.antar.lord;                       // "mercury"
```

This is a synthetic input and the values are the real output of the script. In one result the tropical rasi (Pisces), the Dhruva nakshatra and pada, and the Lahiri sidereal rasi, nakshatra and pada all coexist, and they differ: the Dhruva Moon is in pada 2, the Lahiri Moon in pada 1.

`getJyotishChart(input)` takes `date` (a UT instant), `latitude`, `longitude` and optionally `nakshatraFrame` (`"dhruva"` default, or `"lahiri"`; selects which frame drives the karakas' default degree frame and the dashas), `node` (`"mean"` default or `"true"`), `yearLengthDays`, `karakaScheme` (`7` default or `8`), `karakaDegreeFrame`, `timed` (default `true`), `ephemeris` (`"swiss"` default or `"moshier"`), `strictEphemeris` (throw `SwissEphEphemerisMismatchError` if Swiss silently substitutes another ephemeris, for example Moshier outside the installed 1800-2399 files; default `false`) and `through` (exclusive end of dasha generation, default one full cycle). With `timed: false` there is no Moon, lagna, karaka or dasha. `jyotish.method` is `JYOTISH_METHODS`, and `jyotish.ephemerisUsage` (`{ requested, used, substituted, warnings }`) reports which ephemeris actually produced the positions, so a Moshier substitution is never silent.

## Bilingual descriptions

```typescript
import {
  getNakshatraDescription, getNakshatraDescriptionEntry,
  getNakshatraPadaDescription, getNakshatraPadaDescriptionEntry,
  getVimshottariDashaDescription, getVimshottariDashaDescriptionEntry,
} from 'kaabalah/astrology';

getNakshatraDescription('Purva_Bhadrapada', 'pt-BR');
getNakshatraDescriptionEntry('Rohini')?.keywords.en;
getNakshatraPadaDescription('Ashwini', 1, 'pt-BR');
getNakshatraPadaDescriptionEntry('Ashwini', 4)?.keywords.en;
getNakshatraPadaDescription('Revati', 4, 'pt-BR');
getNakshatraPadaDescription('Bharani', 0); // undefined: invalid quarter
getVimshottariDashaDescription('ketu', 'pt-BR');
getVimshottariDashaDescriptionEntry('jupiter')?.keywords.pt;
```

All 27 nakshatras have two-sentence EN/PT reference entries describing deity
associations and traditional electional nature. Use the canonical underscored
`nakshatraId`, rather than the display name. These historical categories describe
the selection of moments; they do not assign personality traits or predict events.
The separate pada bank covers all 108 quarters as natal reference
interpretations, including physical, health, relationship and financial themes
with their qualifications. Each quarter has a separate entry.
`getNakshatraPadaDescriptionEntry(nakshatraId, pada)` and its text counterpart
accept a canonical ID and an integer quarter from 1 to 4; invalid or unwritten
combinations return `undefined`, without falling back to a whole-nakshatra entry.
These are natal reference descriptions, not daily Moon-event interpretations.
The lookup does not calculate a navamsha sign or imply that Dhruva and sidereal
coordinates are equivalent.

The nine lowercase Vimshottari lord keys have general major-period descriptions:
`ketu`, `venus`, `sun`, `moon`, `mars`, `rahu`, `jupiter`, `saturn`, `mercury`.
Placement and aspect qualifications remain in the prose. These getters do not
assess planetary strength or supply antardasha, major/sub-lord pair or Yogini
interpretations.

Entries and keywords are immutable. Portuguese locales start with `pt`;
omitted and other string locales select English. Invalid keys return `undefined`.
These lookups use the identifier already calculated in your chosen frame and do
not recalculate positions, change frames or generate period dates.

## Dhruva method, as implemented

`JYOTISH_METHODS.dhruva` is the authoritative statement. Its constants are fixed in `DHRUVA_CONSTANTS` and are never calibrated against a chart.

| Element | Implementation |
|---|---|
| Anchor | Galactic Center Sgr A*, ICRS right ascension 266.40499 degrees, declination -28.93617 degrees |
| Anchor frame | FK5 mean equator and equinox **of date**: ICRS to FK5 J2000 frame bias (USNO Circular 179), then bias-free IAU 2006 (Capitaine) precession; no nutation. Equivalent to Astropy `ICRS -> FK5(equinox=Time(jd, format='jd', scale='utc'))` |
| Time scale of the equinox | The input Julian date is read on the UTC scale and converted UTC to TAI to TT (leap seconds, then +32.184 s) |
| Origin | `zeroRA = (GC_RA_of_date - (246 + 2/3)) mod 360` |
| Body position | `nakPos = (planet RA of date - zeroRA) mod 360`, where the RA is the Swiss geocentric **apparent** equatorial right ascension (`SEFLG_EQUATORIAL`: true equator and equinox of date, with nutation, aberration and light-time), keeping each body's **actual ecliptic latitude** |
| Sectors | 27 equal sectors of 40/3 degrees, `index = floor(nakPos / (40/3))`; `pada = floor(4 * elapsedFraction) + 1` (4 padas of 10/3 degrees) |
| Lagna | RA of the tropical ASC at ecliptic latitude 0 with the true obliquity: `atan2(sin(lambda) cos(eps), cos(lambda))` |
| Nodes | Latitude-0 node point. **Mean node is primary**; the true node is exposed as a variant (`nodeVariants`). Ketu is the antipode of the corresponding Rahu (RA + 180, declination negated) |
| Dasha year | `yearLengthDays` 365.2422 by default |

It is **not** ecliptic longitude minus the Lahiri ayanamsa and **not** Swiss sidereal mode 36; a mode number alone does not establish equivalent coordinates. Retaining the planet's latitude matters: Mercury, for example, gives a wrong result if its RA is replaced by a zero-latitude ecliptic projection.

**Mixed mean/apparent caveat.** The Galactic Center anchor is a *mean* FK5 position of date (no nutation), while the bodies use *apparent* equatorial coordinates (with nutation, aberration, light-time). The resulting difference is at most about 0.005 degrees. Do not "correct" one side without changing the method identity.

A Dhruva point (`DhruvaPoint`) carries `nakPos`, `nakshatraIndex`, `nakshatraNumber`, `nakshatraId` (for example `Purva_Bhadrapada`), `nakshatra`, `pada`, `elapsedFraction`, `lord` (Vimshottari lord), `rightAscension`, `declination`, the tropical `longitude`/`latitude`, and `tropical` (rasi, `degreeInSign`). The chart's `origin` records the Julian day, the GC right ascension and declination of date, `zeroRightAscension` and the constants. Lower-level functions: `getDhruvaOrigin`, `dhruvaPlacementFromRightAscension`, `dhruvaPointFromBody`, `dhruvaKetuFromRahu`, `dhruvaLagnaFromAscendant`, `icrsToFk5OfDate`, `utcJdToTtJd`, `nakshatraFromPosition`.

## Lahiri comparison

`jyotish.lahiri` (`calculateLahiriChart`) is the conventional comparison. Planets come from Swiss in sidereal mode 1 (Lahiri) with `SEFLG_SIDEREAL`, apparent, nutation included. The ayanamsa is read back from the same engine as the tropical minus sidereal longitude of the Sun at that instant, i.e. the true (nutation-included) ayanamsa, and the sidereal ascendant is the tropical ASC minus that same value, so planets and ascendant sit in one frame. Nakshatras and padas are `sidereal longitude / (40/3)` on the ecliptic. Houses are whole-sign counted from the sidereal ascendant's sign (`wholeSignHouse` on each point; absent when untimed). The saved Lahiri comparison used a 365.25-day dasha year, exposed as `DASHA_YEAR_LENGTH_REFERENCES.lahiriReference`; that is a reference configuration, **not** a claim about every Lahiri practitioner. The Swiss sidereal mode is process-wide state; it is set, used and reset synchronously, so tropical and other-frame calculations are unaffected.

## Chara karakas

`calculateCharaKarakas(inputs, { scheme, degreeFrame, node })` (also `jyotish.karakas`) ranks the bodies by degree within the sign, descending: the highest degree is the Atmakaraka. The `7` scheme excludes Rahu; the `8` scheme adds Rahu with ranking value `30 - degreeInSign` (it moves retrograde), and the node used (`mean` or `true`) is echoed in `rahuConvention`. The frame of the degree is an explicit input and echoed (`tropical` or `sidereal`): by default `getJyotishChart` ranks **tropical** degrees for the Dhruva frame (what the reference dataset did) and **sidereal** degrees for the Lahiri frame (the traditional practice). Ties within `tieToleranceDegrees` (default `1e-9`) are ordered by a fixed canonical order, flagged `tied: true` and listed in `tieGroups`, so you can apply your own tradition.

## Vargas and vargottama

`getVarga(longitude, division)` gives the divisional placement of one ecliptic longitude (`SUPPORTED_VARGAS`: D1 to D60, Parashari rules) and `getVargaChart(points, division)` maps a record of longitudes, with whole-sign houses from the varga lagna when a `lagna` key is present. Both are pure arithmetic on the longitude they are given and never convert frames.

`isVargottama(longitude)` is true when the longitude holds the same sign in the D1 and the D9: the first navamsa (0 to 3°20') of a movable sign, the fifth (13°20' to 16°40') of a fixed sign and the ninth (26°40' to 30°) of a dual sign. Every D9 placement of `getVargaChart` carries the same answer as `vargottama`; the other divisions do not carry the field. A second argument compares the D1 with another division.

```typescript
import { getVargaChart, isVargottama } from 'kaabalah/astrology';

isVargottama(135);    // true: 15 Leo, fifth navamsa of a fixed sign
isVargottama(209.61); // false: 29.61 Libra is Gemini in the D9

const d9 = getVargaChart({ lagna: 32.56, sun: 209.61, venus: 135 }, 9);
d9.placements.venus.vargottama; // true
d9.placements.sun.vargottama;   // false
```

**Frame.** The D1 sign is the sign of the longitude you pass. With the library's own points that is the **tropical** rasi (`jyotish.dhruva.points[body].longitude`, the tropical longitude of date, which is what `kaabalah astrology:varga` uses), so "same sign" means the same tropical sign in the rasi and the navamsa. Pass sidereal longitudes (`jyotish.lahiri`) to get the sidereal answer; the two differ for most charts.

## Dashas

`generateDashaSchedule`, `generateVimshottariDasha`, `generateYoginiDasha` produce maha and antar schedules; `findActiveDasha(schedule, asOf)` returns the active maha and antar.

- **Birth balance**: the Moon's nakshatra lord's maha began `elapsedFraction * mahaYears * yearLengthDays` days **before** birth. That pre-birth start is kept as the first maha's `start` (`startsBeforeBirth: true`); `schedule.balance` reports the elapsed and remaining fraction, days and years.
- **`yearLengthDays` is mandatory per call** and echoed. Named references: `DASHA_YEAR_LENGTH_REFERENCES.dhruva` = 365.2422 and `.lahiriReference` = 365.25.
- **Vimshottari**: 120 years, lords `ketu venus sun moon mars rahu jupiter saturn mercury` with years `7 20 6 10 7 18 16 19 17`. Antar lengths are proportional: `mahaLength * antarLordYears / totalYears`, starting from the maha lord.
- **Yogini**: 36 years, lords `mangala pingala dhanya bhramari bhadrika ulka siddha sankata` with years 1 to 8, starting at `(nakshatraNumber + 3) mod 8` (a remainder of 0 is Sankata). This convention is implemented but **was not matched to a Kala Yogini export**: treat the Yogini schedule as unvalidated.
- **Half-open intervals**: `[start, end)`; a boundary instant belongs to the period that starts there. By default antars of the first maha that ended on or before birth are omitted (`includePreBirthAntars` keeps them).
- Generation is bounded by `through` (default one full cycle after birth) and `maxMahaPeriods` (default 200; `truncated` reports a stop).

## Panchanga

`getPanchanga({ date, latitude, longitude, timeZoneSettings? })` returns the five limbs of the almanac day that contains `date`. The day is the **vara**, from one sunrise to the next at the place; before sunrise `date` still belongs to the previous vara. Longitudes are Lahiri sidereal (Swiss mode 1, true ayanamsa), geocentric apparent of date. The result holds calculation data only, with no interpretation text.

| Limb | Rule |
|---|---|
| Vara | Weekday of the sunrise in the given zone (`Ravivara` … `Shanivara`), with its planet |
| Tithi | `floor((Moon − Sun) / 12°) + 1`: 1–15 shukla paksha (ends at Purnima), 16–30 krishna paksha (ends at Amavasya) |
| Nakshatra | Moon's sidereal longitude in 27 sectors of 13°20′ |
| Yoga | `(Sun + Moon)` sidereal in 27 sectors (Vishkambha … Vaidhriti) |
| Karana | Half tithi, `floor((Moon − Sun) / 6°)`: Kimstughna, Bava … Vishti eight times, then Shakuni, Chatushpada, Naga |

Each limb comes as `{ atSunrise, atDate, spans }`. `atSunrise` is the limb that names the day, as almanacs print it. `spans` lists every limb running during the vara, with exact `start` and `end` times from the shared root solver, so the first span can start before sunrise and the last can end after the next sunrise.

**Sunrise.** By default the sunrise is the Hindu rising, which is how Indian panchangs print it: the centre of the disc on the geometric horizon with no refraction (Swiss `SE_BIT_HINDU_RISING`). `sunriseDefinition: 'upper-limb-with-refraction'` selects the almanac sunrise of `getPlanetaryHours` instead, about four minutes earlier in India. The sunrise only decides the vara and which limb is "at sunrise"; the limb boundaries do not depend on it.

**Sarvartha Siddhi.** `specialYogas.sarvarthaSiddhi` uses the weekday–nakshatra table of the **Muhurta Chintamani** (Daivajña Rāma, 1600 CE), Śubhāśubha prakaraṇa 1.28–29. The verse names the nakshatras by their deities, and it says it reports earlier authorities ("kathitāni pūrvaiḥ"). Later panchang sites disagree with each other on this table, so the library follows the verse. `SARVARTHA_SIDDHI_SOURCE` holds the transliterated verse and its decoding.

| Vara | Nakshatras |
|---|---|
| Sunday | Hasta, Mula, Uttara Phalguni, Uttara Ashadha, Uttara Bhadrapada, Pushya, Ashwini |
| Monday | Shravana, Rohini, Mrigashira, Pushya, Anuradha |
| Tuesday | Ashwini, Uttara Bhadrapada, Krittika, Ashlesha |
| Wednesday | Rohini, Anuradha, Hasta, Krittika, Mrigashira |
| Thursday | Revati, Anuradha, Ashwini, Punarvasu, Pushya |
| Friday | Revati, Anuradha, Ashwini, Punarvasu, Shravana |
| Saturday | Shravana, Rohini, Swati |

The verse gives only the pairs. A window here is the overlap of the vara with a listed nakshatra, the usual almanac reading. No later exclusions (Rahu Kala, Vishti karana, tithi or eclipse rules) are applied.

```typescript
import { getPanchanga } from 'kaabalah/astrology';

const p = getPanchanga({
  date: new Date('2026-11-25T06:30:00Z'),
  latitude: 23.1765,
  longitude: 75.7885,
  timeZoneSettings: { timeZone: 'Asia/Kolkata' },
});
if (p.available) {
  p.vara.name;                                    // "Budhavara"
  p.tithi.atSunrise;                              // { number: 16, paksha: "krishna", name: "Pratipada", ... }
  p.tithi.spans[1].start;                         // Dwitiya from 16:50:44 IST
  p.nakshatra.atSunrise.id;                       // "Rohini"
  p.specialYogas.sarvarthaSiddhi.windows.length;  // 2: Rohini, then Mrigashira
}
```

**Validation.** For Ujjain on 25 November 2026, every tithi, nakshatra, yoga and karana boundary and both Sarvartha Siddhi windows fall inside the minute printed by Prokerala's panchang (Lahiri). That page truncates times to the minute. The sunrise agrees within one minute; the city's exact coordinates are not printed. The test suite also checks that Shukla Pratipada starts at the solved new moon.

### Month, year, day periods and muhurtas

Each of these depends on a convention choice. The one used is stated in `method`:

- **`masa`**: the amanta month (new moon to new moon) that contains the sunrise. It is named by the Sun's Lahiri sign at its opening new moon plus one, so Mina gives Chaitra. It is **adhika** when the Sun changes no sign before the closing new moon. `purnimanta` gives the krishna paksha the next month's name, except in an adhika month, which is the same lunation in both counts. `ritu` is the season of the lunar year: two months each, from Vasanta. A month in which the Sun changes two signs is **kshaya**, defined in Bhaskara II's *Siddhanta Shiromani* (1150), Madhyamadhikara, adhimasa verse 6. It carries two names: under the present rule (Sewell & Dikshit, *The Indian Calendar*, Art. 46) it is named by its first sankranti, and `absorbs` holds the dropped second name. `sankrantis` counts the sign changes: 0, 1 or 2. Between 1900 and 2170 the ephemeris finds three kshaya months:
  - 16 Nov – 16 Dec 1963: Kartika, absorbing Margashirsha
  - 14 Jan – 13 Feb 1983: Pausha, absorbing Magha
  - Dec 2123 – Jan 2124

  Each lies between two adhika months, as Bhaskara says it must.
- **`year`**: the Chaitradi luni-solar count. `shaka` is the Gregorian year in which amanta Chaitra began, minus 78. `vikram` is `shaka + 135`. `samvatsara` is index `(shaka + 11) mod 60` of the 60-year cycle, from Prabhava; Shaka 1948 is Parabhava; this is the South Indian name, where no year is ever skipped. `jovianSamvatsara` is the North Indian (Barhaspatya) name, which goes with the Vikram year. That cycle follows Jupiter's mean motion, so its years are 361 days long, and about every 85 years one name is skipped.
  - **Rule:** the name current at the Mesha sankranti of the Shaka year names the whole year. It is computed by Surya Siddhanta 1.55 with the bīja correction, in the integer form of Sewell & Dikshit Art. 59c (`jovianSamvatsaraSuryaSiddhanta`). This is the rule current almanacs follow. Sewell gives it for years after 1500 CE. Under it, Manmatha was skipped in 1942 and Durmati is skipped in 2027.
  - **Older rule:** Brihat Samhita 8.20–21 is available as `jovianSamvatsaraBrihatSamhita`. It disagrees for Vikram 2083: it gives Raudra, the name Patrika prints, where the default gives Siddharthi.
  - **Spelling:** `SAMVATSARA_NAMES` uses Prokerala's spellings (Angira, Dhatru, Isvara, Bahu Dhanya, …, Anala, Kalayukta, Dundhubhi, Raktaksa, Kshaya). Both the Shaka and the Vikram names match Prokerala's daily panchang for every year from 1980 to 2026.
- **`dayPeriods`**: sunrise to sunset is cut into 8 equal parts. **Gulika** and **Yamaganda** are Saturn's and Jupiter's parts when the parts go to the weekday lords in order from the lord of the day, the rule of the upagrahas in Brihat Parāśara Horā Śāstra (`dayPartOfPlanet`). **Rahu Kala** follows the South Indian almanac table (`RAHU_KALA_PARTS`: Sun 8, Mon 2, Tue 7, Wed 5, Thu 6, Fri 4, Sat 3). No classical text for that table was found.
- **`muhurtas`**: 15 equal day muhurtas (sunrise to sunset) and 15 equal night muhurtas (sunset to next sunrise). `abhijit` is day muhurta 8. `brahma` is muhurta 14 of the night before this vara, so it ends one night muhurta before the sunrise. Both are proportional, and no weekday exclusions are applied. Some almanacs drop Abhijit on Wednesdays and print Brahma muhurta as a fixed 48 minutes.

For Ujjain on 25 November 2026, these match Prokerala to the printed minute: Kartika / Agrahayana (Margashirsha), Shaka 1948 Parabhava, Vikram 2083, Rahu Kala 12:13–13:34, Yamaganda 08:11–09:32, Gulika 10:53–12:13, and the 8th day muhurta 11:52–12:35. The tests also check the adhika months of 2023 (Shravana) and 2026 (Jyeshtha), and the Shaka year change at Ugadi.

### Muhurta names, Dur Muhurta, Varjyam, Amrit Kaal and Choghadiya

For each of these the library uses the oldest text found that defines it:

| Field | Source | Rule |
|---|---|---|
| `muhurtas.*.vedicName` | Taittiriya Brahmana 3.10.1.1–3 | Fifteen day and fifteen night names, with separate lists for the bright and the dark fortnight (`VEDIC_MUHURTA_NAMES`). The list follows the paksha of the tithi at sunrise. |
| `muhurtas.*.deity` | Narada Samhita 9.1–3; also Muhurta Martanda and Muhurta Chintamani 6.52–53 | The presiding deities, Rudra … Bhaga by day and Isha … Vayu by night (`MUHURTA_DEITIES`). Day 8 is Abhijit. The common modern list (Rudra, Ahi, Mitra … Satamukhi, Puruhuta …) is this scheme with synonyms and corruptions. |
| `muhurtas.durMuhurtas` | Narada Samhita 9.4–5 = Muhurta Chintamani 6.54 | By weekday (`DUR_MUHURTAS`): Sun day 14; Mon day 9, 12; Tue day 4, night 7; Wed day 8; Thu day 6, 12; Fri day 9, 4; Sat day 1, 2. The verse does not say whether Tuesday's Agni is a day or night muhurta. It is read as night 7, the only muhurta Agni presides over. |
| `varjyam` | Narada Samhita (vivaha) 55–60 = Vasishtha Samhita = Muhurta Martanda = Muhurta Chintamani 6.49–51 | Each nakshatra has a start ghaṭī out of 60 (`VARJYAM_START_GHATI`), scaled to its real length. The window lasts 4 ghaṭīs. |
| `amritKaal` | Verse quoted in the Sanskrit commentary on Prashna Marga 21 (Kerala, 1649) | Same shape, with `AMRIT_KAAL_START_GHATI`. The same commentary first gives a simpler rule, the 4 ghaṭīs after Varjyam, which is not used. None of the older muhurta texts has an Amrit Kaal table. |
| `choghadiya` | No classical text found | A later North Indian / Gujarati convention. Daytime and night are each cut into 8. Day slots start with the weekday's lord and step 5 weekdays. Night slots start with the lord 4 weekdays on and step 4. Each lord gives a name: Sun Udveg, Moon Amrit, Mars Rog, Mercury Labh, Jupiter Shubh, Venus Char, Saturn Kaal (`choghadiyaPlanet`). |

Varjyam and Amrit Kaal windows are listed when they overlap the vara, and they are not clipped. For Ujjain on 25 November 2026 every value matches Prokerala to the printed minute:

- Varjyam 13:32–14:57 (Rohini) and 01:32–02:57 (Mrigashira)
- Amrit Kaal 17:46–19:10
- Dur Muhurta 11:52–12:35
- Choghadiya starting with Labh 06:51–08:11, and Thursday's full day and night sequences

Variants not followed: a Kerala Varjyam table (Raman's notes to Prashna Marga) gives Ardra 11, Hasta 22 and Mula 20. A "Madhaveeya" Amrit Kaal table gives different values, for example Rohini 35.

Where the Sun does not rise or set, the result is `{ available: false, reason }`.

## Validation statement

What was and was not checked, exactly as recorded in `JYOTISH_METHODS.validation`:

- **Placements and dates are validated separately.** Two Kala comparison cases reproduce **18/18** nakshatra and pada placement labels.
- Their **first-major start dates** retain residuals of **-2.368444 days and -11.501848 days** under the Moshier comparison settings. The same comparison run with the production Swiss ephemeris files gives **-2.379069 days and -11.429322 days**, with identical placement labels. The two settings are recorded separately; neither is fitted.
- **No constant was fitted** to remove those residuals, and **exact Kala date parity is not claimed**.
- **Yogini** arithmetic follows the chosen convention above and has not been matched to a Kala Yogini export.
- The frame mathematics (GC anchor to FK5 of date) matches the Astropy-based reference to well under `1e-6` degrees on synthetic fixtures; the ephemeris difference between the Swiss files and Moshier is a separate, recorded effect.
- Repository tests use synthetic inputs and independent invariants (sector and pada boundaries, RA wrap, Ketu antipode, durations, half-open boundaries).

Pass `ephemeris: 'moshier'` to reproduce the reference Moshier settings. Do not use a mode number or a different precession formula as a substitute for the Dhruva method.
